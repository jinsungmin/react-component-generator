# commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋으로 저장한다. 이 스킬이 호출되면 별도 승인 절차 없이 바로 커밋한다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경·추적되지 않은 파일을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 내용을 읽는다.
- `git log --oneline -10`으로 최근 커밋 스타일을 참고한다.
- 저장소가 아니면(`git rev-parse` 실패) 커밋할 수 없다고 알리고, `git init`은 사용자가 요청할 때만 한다.
- 변경사항이 없으면 그렇게 알리고 종료한다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 목적(예: 기능 추가와 설정 변경)은 나눈다.
- 파일 단위가 아니라 변경 의도 단위로 묶는다. 한 파일에 목적이 섞여 있으면 `git add -p` 대신 사용자에게 분리 여부를 묻는다(`-i` 대화형 옵션은 이 환경에서 쓸 수 없다).
- 다음 파일은 커밋 대상에서 제외하고 사용자에게 알린다.
  - `.env`, 키·토큰·인증서 등 비밀 정보
  - `node_modules/`, 빌드 산출물, 임시 파일
  - 의도와 무관해 보이는 파일

### 3. 한국어 커밋 메시지 작성
형식:

```
<type>: <요약>

<본문(선택): 무엇을, 왜 바꿨는지>

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

- **type**
  - `feat`: 새 기능
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 구조 개선
  - `chore`: 설정, 의존성, 문서, 빌드 등 그 외
- **요약**: 50자 안팎, 명령형이 아니라 변경 내용을 담은 간결한 한국어, 마침표 없음.
  - 좋은 예: `feat: 생성 결과 카드를 레트로 창 스타일로 변경`
  - 나쁜 예: `fix: 수정`, `chore: 여러 가지 변경`
- 본문은 요약만으로 이유가 드러나지 않을 때만 쓴다.
- 코드 식별자와 기술 용어는 원문 그대로 쓴다.

### 4. 커밋
1. 단위별로 `git add <파일들>` 후 `git commit`을 실행한다. `git add -A`나 `git add .`는 쓰지 않고 파일을 명시한다.
2. 분류가 모호하거나 한 파일에 목적이 섞여 있어 판단할 수 없을 때만 사용자에게 묻는다. 그 외에는 묻지 않고 진행한다.
3. 완료 후 `git log --oneline -n <커밋 수>`로 커밋 목록과 포함 파일을 보여 준다.

## 금지 사항
- `--no-verify`, `--amend`, `push`, `reset --hard` 등은 사용자가 명시적으로 요청하지 않으면 쓰지 않는다. 훅이 실패하면 원인을 고쳐 새 커밋을 만든다.
- 커밋 메시지에 비밀 정보나 내부 경로를 넣지 않는다.
