# TDD Rule

> **경고: 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 1. 적용 기준

### 반드시 TDD를 적용한다

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리, 에러 분기)
- 유틸 함수 (순수 함수, 데이터 변환)
- 버그 수정 (먼저 버그를 재현하는 실패 테스트를 작성한다)

### TDD가 불필요하다

- 타입 정의 (`interface`, `type`)
- 설정 파일 (`vite.config.ts`, `tsconfig*.json`, ESLint 설정 등)
- 순수 UI (로직 없는 마크업/스타일링)
- SQL (스키마, 마이그레이션, 단순 쿼리)

판단이 애매하면 **로직(분기, 계산, 상태 변화)이 있으면 적용**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

1. **하나의 동작 = 하나의 테스트**. 한 테스트에 여러 동작을 섞지 않는다.
2. 테스트 이름은 기대 동작을 설명한다.
3. **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
4. **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 설정 오류로 실패한 것은 RED가 아니므로 테스트부터 고친다.

### GREEN: 최소 구현

1. 테스트를 통과시키는 **최소한의 코드만** 작성한다.
2. **YAGNI**: 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 추가하지 않는다.
3. **신규 테스트와 기존 테스트가 모두 통과**하는지 전체 실행으로 확인한다.

### REFACTOR: 정리

1. 중복 제거, 이름 개선, 헬퍼 추출만 한다.
2. 리팩터링 중 **테스트는 항상 green**을 유지한다. 변경마다 실행한다.
3. **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 반복

REFACTOR가 끝나면 **다음 동작에 대한 RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. 해당 프로덕션 코드를 **삭제한다.**
2. **RED부터 재시작**한다.
3. **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 남겨 둔 코드를 보면서 테스트를 쓰면 구현에 맞춘 테스트가 된다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순한 코드가 가장 자주 조용히 깨진다. |
| "나중에 테스트를 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 버그를 못 잡고, 대개 쓰이지 않는다. 지금 쓴다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 회귀 수정으로 더 많은 시간을 쓴다. TDD가 더 빠른 경로다. |
| "삭제하면 낭비다" | 매몰 비용 오류다. 이미 쓴 코드를 유지할 때의 위험이 다시 쓰는 비용보다 크다. 삭제한다. |
| "프로토타입이다" | 프로토타입은 쉽게 프로덕션이 된다. 버릴 코드라면 테스트 없이 남기지 말고 버려라. 남길 코드라면 TDD를 적용한다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 있으면 **그 규칙이 우선**한다.
- **이 파일은 기본값(fallback)이다.** 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
